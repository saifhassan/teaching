# Semester OOP Project — Grading criteria (rubric)

**Total marks: 5** (course project component)  
**Task reference:** See **`OOP-Semester-Project-Instructions.md`**.

These criteria describe how we assign the **5 marks**. We use **partial credit** where a submission is only partly complete. **Academic integrity** and **citations** (for adapted tutorials/snippets) are expected, as in the project instructions.

---

## Mark breakdown

| Area | Marks | What we look for |
|------|------:|------------------|
| **Submission package & consistency** | **1** | **All required channels are done:** public **GitHub** with full source; **eLearning `.zip`** with same folder of sources + same **root `README.md`**; **video** link works and is **≤ 5 minutes**. **Names, CMS/IDs, and section** match across **GitHub README**, **zip README**, and **video** (each member visible/speaking per instructions). Missing or inconsistent items lose marks here. |
| **README & reproducibility** | **1** | **Project title** and **short description**; **group list** (name, CMS/ID, section per person); **purpose** and **main modules** (packages / class groups) are clear; **how to compile and run** (JDK version, `main`, and any DB/SQL or config steps). A grader or peer can follow the README on a **clean** machine and get the app running. Broken links or missing run steps cost marks. |
| **OOP design & course concepts** | **1.5** | A **coherent** application (not one giant class with no structure). Evidence of **classes and objects**; **encapsulation** (private state, sensible accessors where needed); **inheritance** and/or **interfaces** and/or **polymorphism** where they fit the domain; **abstract classes** if appropriate; use of **collections**; **file or database** use if the project needs persistence; **exception handling** in sensible places. We reward **clear modeling** and appropriate use of topics from the **course**, not OOP “buzzwords” with no real use. |
| **Implementation quality** | **1** | **Organization:** sensible packages or file layout, separation of concerns (e.g. model / services / UI or console). **Clarity:** readable names, not unnecessary duplication, basic **validation** where user input or data matters. Small deductions for fragile code only if it **clearly** breaks main flows. |
| **Demo & functionality** | **0.5** | **Video:** Covers **purpose**, **why this project**, and **core modules**; **every** member **speaks**; time **≤ 5 min**. **Software:** the **stated** features in the README are **demonstrated**; the app behaves as a small **end-to-end** system for its topic (not a stub with only prints). |

**Total: 1 + 1 + 1.5 + 1 + 0.5 = 5**

---

## General notes (for students)

- **Partial credit:** You can still earn part of a category if some requirements are met (e.g. good OOP with a README that omits the video link).
- **Honest attempts:** If the project does not run end-to-end, you may still earn marks in **OOP design** and **code organization** if the design and code are **readable** and show the right **ideas**—but **“runs from README”** and **full submission** are still important.
- **Integrity:** Unattributed large copy-paste or work that the group **cannot explain** in **video/viva** may be treated as an integrity case, not only a mark deduction.
- **Trivial scope:** A project that ignores the “minimum expectations” in the project instructions (almost no OOP, no real structure) may be **capped** in the **OOP** and **functionality** rows even if it compiles.
